# PR Description and Issue

Use for pull request descriptions and engineering issues.

- Use sentence case and standard punctuation. Avoid emoji, except one when it materially helps.
- Be as long as the technical account requires.
- Lead with what changed and why, not implementation chronology.
- Structure as bug or need, shared cause, what the change does, side refactors or deletions, then pointers such as ADRs and follow-ups.
- State what happens, what the user sees, and every concrete number. Avoid scene-setting or narrative drama.
- Avoid punchline staccato. Blog rhythm does not belong in a bug description.
- Keep one mild flourish at most. PR bodies stay flat even when review comments can carry dry humour.
- Clean grammar without inventing certainty. Preserve unresolved edge cases explicitly.
